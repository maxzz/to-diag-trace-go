I found **two separate bugs** in the Go port. The screenshot shows both at once because the DPLogs error is from a prior gather attempt, while the ETW error blocks starting trace.

## 1. `ETW: StartTrace failed: 161` (ERROR_BAD_PATHNAME)

**Root cause:** In `diag/7-utils-etw.go`, the `EVENT_TRACE_PROPERTIES` struct had the wrong layout for 64-bit Windows.

`LoggerThreadId` is a `HANDLE` (8 bytes on amd64), but the Go port used `uint32` (4 bytes). That shifted `LogFileNameOffset` and `LoggerNameOffset` by 4 bytes, so `StartTraceW` read the wrong offset and treated the log file path as invalid.

The original C++ code uses the Windows SDK struct, which has the correct size automatically.

**Fix applied:**
- Changed `LoggerThreadId` from `uint32` to `uintptr`
- Switched `EnableTraceEx2` back to `EnableTrace` (matching the original C++ `EtwUtils.cpp`)

Verified locally: `StartTrace` returns success with the corrected struct.

## 2. `event log DPLogs: exit status 87` (ERROR_INVALID_PARAMETER)

**Root cause:** The DPLogs export used the wrong `wevtutil` argument order.

The Go port had:
```text
wevtutil epl /q:<query> <output.evtx>
```

But `wevtutil epl` expects:
```text
wevtutil epl <PATH> <TARGETFILE> [/options]
```

So `/q:...` was parsed as the log name, which is invalid.

The original C++ code does not use `wevtutil` at all — it calls `EvtExportLog()` with a multi-channel XML query directly (`TraceGatherer.cpp`).

**Fix applied:** Write the query XML to a temp file and export with:
```text
wevtutil epl <queryfile> <output.evtx> /sq:true /ow:true
```
